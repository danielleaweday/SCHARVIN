How to Read This Document

Key

Every interactive control in ANCRID is documented as a small connected flow: what the user clicks, what the system does, and where each outcome leads. Shapes and colours carry fixed meaning — they are not decorative.

Shape & colour vocabulary

Behaviour classification

Every flow carries one of four labels. This prevents prototype behaviour from silently becoming a production requirement.

LabelMeaningHow the developer should treat it
Intended Supported by the ANCRID product specification and Master Workflow. Build this. The current application may or may not already do it correctly.
Observed What the current application actually does today. Recorded for reference only. Shown where it differs from Intended. Do not treat as a target.
Decision The application and the specification disagree, or the behaviour is undefined. Do not guess. Requires a product decision before this control is built.
Proposed Needed to complete the experience, but not yet approved. Awaiting sign-off. Drawn dashed in diagrams.
Dead A control is rendered in the UI but has no handler attached. Either wire it to the flow specified here, or remove it from the page.

Target-State Language

This document describes the self-hosted product. Prototype-platform specifics are translated: a vendor session token becomes an authenticated ANCRID session; vendor object storage becomes the approved media storage service; a vendor AI key becomes the configured AI service. Where the replacement service does not yet exist, that is called out explicitly rather than assumed. A full translation table appears on the final page.

Scope Note — Authentication

The ANCRID Master Workflow states that no module implements its own login and that every application consumes ANCRID. ANCRID itself is the identity provider, so it necessarily owns the sign-in surfaces documented on pages 03–04. The consumption side — other modules accepting an ANCRID session instead of presenting their own login — is specified on page 10 (SSO Handshake) and is currently the largest gap between specification and build.

Remove Before Deployment — Prefilled Credentials

The login form currently ships with a working email and password pre-populated in the input fields, and the same pair printed on-screen in a visible demo panel. This is prototype scaffolding. It must not reach any shared or public environment. Observed — not an intended behaviour, and deliberately excluded from the flow above.

Decision Required — Missing Account-Recovery Paths

There is no forgotten-password flow, no password-change surface, and no email-verification step anywhere in ANCRID. For the identity provider of the entire ecosystem, a user who loses their password currently has no self-service route back in. Three flows require specification before launch: request reset · consume reset link · change password while signed in.

Session Lifecycle & Route Guard

Every Protected Page

This flow runs on every navigation into /app/*. It is the single gate protecting all 16 authenticated destinations.

Entering a protected route

Decision Required — Return-To-Destination After Re-Authentication

A user whose session expires mid-task is redirected to the login screen and, after signing in, is delivered to the Overview page — not back to what they were doing. For a user part-way through editing their identity or assembling a Booking Packet, the work context is lost. The dashed step above is the proposed correction: capture the attempted route, then restore it after successful authentication.

Signing out

Intended — Sign-Out Must Be Unambiguous

The user is returned to the Landing page in both branches, so sign-out always appears to succeed. That is the correct user-facing behaviour. However the control is an unlabelled icon in the sidebar footer. Proposed Give it a visible text label or an accessible name, and confirm before signing out if unsaved edits exist on the Settings page.

Identity & Settings

The Only Write Surface

Settings is the single page in ANCRID where a user changes stored data. Identity is its read-only counterpart. Everything else in the application is display-only.

Editing and saving identity Intended

Image upload lifecycle — headshot and banner

Decision Required — Two-Step Save Is Easy to Lose

Upload and save are separate actions. A user who uploads a headshot, sees the preview update and a success toast, then navigates away, loses the image — it was never attached to their profile. The success toast actively implies otherwise. Options: persist the image URL immediately on upload; or keep the two-step save but warn on navigation with unsaved changes and reword the upload toast.

Decision Required — Upload Constraints Undefined

The file picker accepts any image type with no stated maximum size, minimum dimensions, or aspect-ratio guidance, and there is no crop step. A headshot and a wide banner have very different shape requirements. Specify: accepted formats, size ceiling, recommended dimensions per slot, and whether a crop tool is in scope.

Record Surfaces — Shared Pattern

9 Pages, One Flow

Nine destinations are read-only record lists that behave identically. They are specified once here rather than nine times. Each fetches its own collection on entry and renders a card or row list.

The shared pattern

Collaborations/ancrid/collaborationsNoneCollaborator, role, project, verification badge.
Skills/ancrid/skillsNoneLevel, project count, years, verifying body.
Education/ancrid/educationNoneInstitution, degree, years, capstone, mentors.
Professional/ancrid/historyNoneRow list of role, organisation, type, years.

Connected Ecosystem/ancrid/ecosystemNoneModule status grid. See page 08.

Applies to All Nine — No Failure State Exists

None of these pages handles a failed request. If the collection cannot be loaded, the page renders as though the user simply has no records — an empty Credentials page looks identical whether the user has earned nothing or the service is unreachable. For a verified-identity product this is a meaningful misrepresentation. Every record surface needs three distinct states: populated, genuinely empty (with guidance on how to earn the first record), and failed-to-load (with a retry).

Decision Required — These Records Are Read-Only

A creator cannot add, edit, or remove any skill, credential, achievement, collaboration or education entry from within ANCRID. The specification describes these as accumulating from verified ecosystem activity, which implies they arrive from other modules rather than by self-entry. Confirm the intent: if records are populated exclusively by upstream modules, each empty state should say which module produces that record type, so the user knows where to go.

Portfolio & Network

Filtering & Search

Portfolio — medium filter

Network — directory search and filters

Decision Required — Search Fires On Every Keystroke

The directory re-queries the server on each character typed, with no debounce and no loading indicator. On a large directory this produces a request per keystroke and results that visibly churn while typing. Proposed Debounce input by roughly 300 ms, show a loading state during the request, and discard responses that arrive out of order.

Dead Controls On This Page Pair

Portfolio's "Open" and Network's "View" are both rendered as interactive buttons and both do nothing when clicked. They are the two most prominent affordances on their respective cards, so a user will reasonably expect a detail view. Decide per control: wire it to a detail surface — which does not currently exist and would need specifying — or remove the button.

Connected Ecosystem & Creator Journey

Display Surfaces

Connected Ecosystem

Presents each ANCR module and its connection state around a central ANCRID hub. This is the user-facing expression of the "one identity, every module" promise, so what it claims matters.

Decision Required — This Page Should Be the Launcher

The ANCRID Master Workflow recommends a central hub from which a user moves into any module without encountering another sign-in. This page already renders exactly that grid — but the cards are inert. Making each card open its module, carrying the ANCRID session, would deliver the recommended experience with the surface that already exists. This is the single highest-value interaction change in ANCRID. It depends on the SSO consumption flow on page 10.

Verify Before Launch — Status Must Be Truthful

Each module card displays a connection status and a last-activity summary. If any of these values are fixed rather than derived from a live check, the page tells a creator their identity is synchronised with modules that are not in fact connected. Requirement: every status shown must reflect a real connectivity result, or be labelled as unavailable.

Creator Journey

The chapter strip is in-page navigation only — it moves the viewport, it does not change route. If the journey has no chapters, the strip and all chapter sections are omitted entirely, leaving only the page heading. Proposed Add an empty state explaining how journey chapters are earned.

The Central Gap — Tokens Are Issued But Never Consumed

This page proves ANCRID can issue a valid identity token. Nothing in the ecosystem currently accepts one. There is no redirect into a module carrying the session, no return path back to ANCRID, and no module-side session establishment. Every other ANCR application presents its own separate sign-in.

Decision Required — Sensitive Data Has No Access Controls

The Medical and Emergency tabs hold health information and third-party contact details. Within ANCRID these sit behind the ordinary session gate with no additional protection, no field masking, and no access logging. They can also be included in a shared Booking Packet (page 11). Specify before any real data is entered: who may view these tabs, whether values are masked by default, whether access is recorded, and the retention and deletion rules that apply.

Decision Required — Fourteen Tabs, No Way to Edit Any of Them

Every mobility tab is read-only. A creator whose passport expires, dietary requirement changes, or emergency contact moves cannot correct any of it from this page. Confirm the source of truth: if this data is maintained elsewhere, each tab should say where and link to it; if ANCRID owns it, editing surfaces need specifying for all fourteen.

Booking Packet Lifecycle

Generate · Share · Revoke

A Booking Packet is a shareable public link exposing a filtered subset of the creator's mobility profile. It is the only feature in ANCRID that publishes private data to an unauthenticated audience, so each control carries real consequence.

Generating a packet

Managing an existing packet

Decision Required — Three Unlabelled Icon Controls, One Destructive

Copy, Open and Revoke are rendered as icons with no text labels, sitting adjacent on each row. Revoke is irreversible and permanently breaks a link that may already be in a promoter's inbox. Proposed Give each control a visible or accessible label, and separate the destructive action from the two safe ones.

Decision Required — Packets Have No Expiry and No Audit

A generated link stays live indefinitely until manually revoked. There is no expiry option at creation, no record of how many times a packet has been opened, and no indication to the creator that a link is being accessed. For a document that can include medical and emergency contact information, this is a significant omission. Specify: optional expiry at generation, an access count per packet, and whether the creator is notified on first open.

Confirm — What Each Visibility Level Actually Exposes

Three visibility levels are offered but the page does not state what each one includes or withholds. A creator choosing "team" over "booking only" has no way to know what changes. Requirement: each level must be described at the point of choice, and the emergency-contact toggle must state plainly that enabling it publishes third-party personal contact details to anyone holding the link.

Public Surfaces

No Session Required

Two surfaces are reachable by anyone holding the address. Both are read-only, both are outside the application shell, and both are the creator's public face.

Public creator identity

Public booking packet

Decision Required — Public Identity Has No Visibility Control

Any creator with a handle has a live public page. There is no setting to make it private, no preview of how it appears to a visitor, and no indication within the application that it is publicly visible. The only hint is a copy-link control in Settings. Specify: a visibility toggle, a preview, and a clear statement in Settings of what a visitor can see.

Intended — Both Surfaces Are Recruitment Points

Each public surface carries a call to action inviting the visitor to claim their own ANCRID. This is correct and should be preserved: the public identity page is the primary organic entry point into the ecosystem, and the flow from visitor to new account should be as short as possible.

Self-Hosted Translation

The prototype was built on a hosted development platform. This document uses neutral, target-state language throughout. Where a replacement service does not yet exist, that is stated rather than assumed — a developer must not read a neutral phrase as an available service.

Blocking Dependency — Media Storage

The image upload flow on page 05 is specified against an approved media storage service. No such service is currently provisioned for the self-hosted build. Until one is chosen and configured, headshot and banner upload cannot function, and the paste-a-URL fallback becomes the only working path — which means every creator image is hot-linked from a third-party host outside your control. This should be resolved early; it is a prerequisite, not a detail.

How to extend this document to the other modules

This specification is the pattern for the remaining ANCR applications. The method that produced it:

  • Inventory every control first. Read each page and record the literal label, what it calls, and what happens on success and failure. Controls with no handler are found this way, not by inspection of the running app.
  • Consolidate repeated patterns. Nine ANCRID record surfaces share one flow. Documenting them once made the difference between a readable specification and ninety pages of near-identical diagrams.
  • Separate intended from observed. Where the build and the specification disagree, say so and mark it for decision. Never let current behaviour silently become the requirement.
  • Name every dead control. A rendered button that does nothing is a defect the user meets directly. List each one and require a decision: wire it, or remove it.
  • State what does not exist. Empty states, error states and missing services are the parts a developer will otherwise invent inconsistently.
