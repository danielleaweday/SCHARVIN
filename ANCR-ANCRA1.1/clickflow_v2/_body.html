01

How to Read & Complete This Document

Key

This document maps the ANCRA design to the behaviour a developer must build. For every element the designer placed on screen, it states what that element is for and what must happen when a user uses it. It is written to be built from — and, where the design is incomplete, to be completed by the team before building.

This Is Not a Defect Report

ANCRA is a design prototype. Its controls are not wired to a backend, and that is expected — it is the reason this specification exists. Nothing in this document reports a control as broken. Every entry describes intended behaviour for the production build on our own infrastructure.

Classification

LabelMeaningWhat you do with it
Specified Defined by the ANCRA product specification or User Flow, or unambiguous from the design itself. Build it as written.
Proposed Behaviour inferred from surrounding context. A reasonable reading, but not confirmed. Confirm or correct. Drawn with a dashed violet outline.
To define The design does not answer this and it cannot be safely inferred. Fill it in. Each carries an ID and a ruled space to write in.
Decision A genuine product choice with more than one defensible answer. Choose. Options are listed where known.

How the fill-in areas work

Where the design leaves a question open, this document does not guess. It leaves you space. Each open item is numbered TD-01, TD-02 and so on, appears at the point in the document where it matters, and is collected into a single register on the final page so you can see how much is outstanding and work through it in order.

TD-00  ·  Example
This is what an open item looks like. The question is stated here, with any context needed to answer it. Write your answer on the ruled lines below — on a printed copy, or in the editable HTML source supplied alongside this PDF.
Answered items should be marked complete in the register on the final page.

What each control specification contains

FieldMeaning
PurposeWhat the user is trying to accomplish by using this control.
On activationWhat the system does when it is used, including what data is sent.
SuccessWhat the user sees, and where they end up.
FailureWhat the user sees, and what is preserved so their work is not lost.
PreconditionsWhat must be true for the control to be available or enabled.

Target Infrastructure

This document describes the build on our own server. Where the prototype relied on a hosted development platform, the capability is named neutrally — a configured AI service, an approved media storage service. Where that capability does not yet exist on our infrastructure, it appears as a cross-screen requirement on page 13 rather than being assumed available.

Identity & Role Model

Foundation

ANCRA presents two experiences — student and faculty. Which one a user receives determines what they can see and do across all 45 routes. This is the foundation every other page depends on.

Intended sign-in and role assignment Proposed

Why This Page Contrasts With the Prototype

This is the one place in the document where current prototype behaviour is worth naming, because it would otherwise mislead. The prototype lets any user switch between student and faculty using a toggle in the top bar, with the role stored in the browser. A developer reading only the prototype would reasonably conclude that role is user-selectable. It is not. Role comes from ANCRID and the user cannot change it.

What each role may reach

RoleReachesMust not reach
StudentDashboard, learning journey, experiences, lessons, assignments, projects, peer reviews, portfolio, graduation, capstones, teams, messages, calendar, achievements, passport, library All faculty routes, all other students' work
FacultyCommand centre, students, approvals, reviews, grading, all authoring tools, analytics, cohorts, creative teams TD-01 — see below
TD-01  ·  Faculty scope
Does a faculty member see all students, or only students in cohorts they teach? This determines whether the roster, grading queue and analytics are filtered by teaching assignment, and whether a cohort-to-faculty relationship needs to exist in the data model.
TD-02  ·  Additional roles
The ANCR ecosystem describes mentors, artists in residence, and institution administrators. Do any of these need an ANCRA experience? If so, list the role and what it reaches. If not, state that ANCRA is student and faculty only.

Learning Flow

Journey → Experience → Lesson

The path a student takes to consume content. Three levels deep, and the reason ANCRA exists.

Lesson Player — control specifications

Play / PauseButtonSpecified
Purpose
Start and stop lesson media.
On activation
Begins playback of the lesson's media from the current position; pause holds position.
Success
Media plays. Elapsed time and remaining duration are visible. Progress is reported periodically so the position survives leaving the page.
Failure
If media cannot load, the player shows a retry affordance and states that the lesson could not be loaded — it must not present as an empty or finished lesson.
Preconditions
Lesson exists and the student is enrolled in the parent experience.
TD-05  ·  Lesson media format and hosting
The design shows a video-style player with a poster image. What media does a lesson actually contain — video, audio, or both? What formats must be supported, where is the media hosted, and is it streamed or downloaded? This determines the media storage requirement on page 13.
If lessons are video, note whether captions and transcripts are required.
Chapter listListSpecified
Purpose
Jump to a named section within the lesson.
On activation
Moves playback to that chapter's start time and marks it as the active chapter.
Success
Playback continues from the chapter start. The active chapter is highlighted.
Preconditions
The lesson defines chapters. If it does not, the list is not shown.
BookmarkButtonProposed
Purpose
Let a student mark this lesson to return to later.
On activation
Saves a bookmark against the student and the lesson.
Success
The control shows a saved state. The bookmark appears in a place the student can find it.
Failure
The control returns to its unsaved state with a brief message.
TD-06  ·  Bookmarks
Two things the design does not answer. Is a bookmark for the whole lesson or a timestamp within it? And where does the student go to see their bookmarks — there is currently no surface listing them. If bookmarks need a home, name it.
DiscussionButtonTo define
Purpose
Open a conversation attached to this lesson.
On activation
See TD-07 — the discussion surface is not designed.
TD-07  ·  Lesson discussion
A Discussion control exists on the lesson, but no discussion screen was designed. Define: is it a thread per lesson visible to the whole cohort, or to a smaller group? Can faculty post and moderate? Are replies threaded? Does it notify anyone? If discussion is out of scope for the first build, say so and the control is removed.
ShareButtonDecision
Purpose
Pass a reference to this lesson to someone else.
Decision
Three defensible options: (a) copy an in-app link usable only by enrolled students; (b) share to a cohort or team inside ANCRA; (c) a public link exposing lesson content outside the programme. Option (c) has content-rights implications and should not be chosen by default.
TD-08  ·  Share target
Choose (a), (b) or (c) above, or describe the intended behaviour.

Not Found — Applies to Both Levels

An unknown experience or lesson identifier must produce the same experience: a clear not-found state inside the application shell, naming what could not be found and offering a route back to the learning journey. The user must not be dropped out of the application.

TD-19  ·  Publishing permission
Can any faculty member publish content that students will see, or does publishing require review or approval by a lead? This affects whether a submitted-for-review state is needed between draft and published.
TD-20  ·  Sequencing and prerequisites
Are lessons and experiences ordered, and must a student complete one before the next unlocks? Or is all published content available at once? This changes the learning journey and the progress model substantially.
TD-21  ·  Curriculum canvas
The Curriculum Builder presents a canvas of blocks. What is a block, and what does arranging them produce? Is the canvas the authoritative programme structure, or a planning view that is then applied?
TD-22  ·  Assignment targeting
The control reads Assign to cohort. Can an assignment also target an individual student or a creative team? Can it be scheduled to release at a future date rather than immediately?
TD-23  ·  Rubric reuse
Is a rubric created once and reused across many assignments, or authored per assignment? If reused, what happens to grades already given when a rubric is later edited?
TD-24  ·  Creative team membership
Who assembles a team — faculty only, or can students form their own? Can a student belong to more than one team? Are teams tied to a specific assignment or persistent across the programme?

AI Course Builder — Decision

The design shows a Compose control that produces a drafted course outline, and a Send to Builder control that hands it onward. The intent is clear: generate a starting draft, then refine it in the Lesson Builder. ANCRA already uses a configured AI service for its student assistant, so the capability exists.

Decide: what the generator receives as input (a topic? a learning objective? an existing curriculum block?), and whether the faculty member reviews the draft before it reaches the Lesson Builder or it lands there directly as an unpublished draft.

The One Rule That Matters Here

An empty record set and a failed request must never look the same. A student whose achievements fail to load must not be shown a screen implying they have earned nothing. Every screen in this pattern needs three distinct states: populated, genuinely empty, and failed — the last with a retry.

How the work in this document depends on itself, and how prototype-platform language maps to our own infrastructure.

Suggested Build Sequence

Several items in this document depend on others and should not be scheduled in parallel:

1. Identity (page 02) — nothing else can be safely deployed without role enforcement.
2. Media playback and file upload (this page) — shared infrastructure that several screens need.
3. Submission and assessment (pages 05, 06, 08) as one workstream — a submission with nowhere to go is not useful, and grading with nothing to grade is untestable.
4. Progress, dashboards and analytics (page 15) — these can only be truthful once real activity exists to compute from.
5. Ecosystem actions (page 14) — gated on other module teams, so treat as a separate track.

Summary

43 open items. Of these, 15 block the build of the screen they affect — mostly concentrated in the learning flow, student submission and the assessment cycle. A further 20 should be answered before those screens are built but do not prevent starting. The remainder are minor or depend on other teams.

The fastest route to a buildable specification is to answer the 15 blocking items first. They cluster into four conversations: what completion and progress mean (TD-04, TD-20, TD-39), what students submit and what happens to it (TD-09, TD-11, TD-12, TD-13, TD-15, TD-17), how assessment works (TD-25, TD-26, TD-28), and infrastructure (TD-05, TD-43, TD-35, TD-01).

How to Return This Document

Answers can be written directly onto a printed copy, or typed into the editable HTML source supplied alongside this PDF — each fill-in area is a labelled block in that file. Once the blocking items are answered, this specification is rebuilt with those answers folded in as Specified behaviour, and the remaining open items carried forward.
