Key

Every interactive control in ANCRA is documented as a small connected flow: what the user clicks, what the system does, and where each outcome leads. Shapes and colours carry fixed meaning — they are not decorative.

Read This First — Scale of the Dead-Control Problem

ANCRA renders 65 buttons that have no handler attached and 13 form fields whose values cannot be read back. This is not a scattering of minor omissions. It includes Approve on faculty submissions, Sign & Return on grading, Publish on lesson authoring, Save & Sign on the student portfolio, and Send Packet on graduation.

Every one of those is an action a user will reasonably believe succeeded. The full register is on pages 12–13. No flow in this document should be built without first resolving whether the control it describes is meant to exist.

Target-State Language

This document describes the self-hosted product. Prototype-platform specifics are translated: a vendor AI key becomes the configured AI service; seeded demonstration records are excluded from intended flows. Where a replacement capability does not yet exist, that is stated rather than assumed. The full translation table is on the final page.

Identity & Persona Model

Read First

ANCRA has two personas — student and faculty — controlling which of the 45 routes are meaningful and what each surface displays. How a user becomes one or the other is the single most consequential behaviour in the application.

How the persona is currently selected Observed

Observed — There Is No Authentication

The ANCRA backend contains no authentication construct of any kind: no session handling, no token verification, no credential check, and no authorisation dependency on any of its 24 endpoints. Persona is a client-side preference stored in the browser and echoed to the server as a query parameter.

Consequently every faculty surface is reachable by any visitor — the command centre, the student roster, grading, approvals, cohort analytics and the entire authoring suite — by clicking a toggle that is permanently visible in the top bar. No flow in this document should be read as implying otherwise until the identity model below is built.

Intended persona model Proposed

Decision Required — Is the Persona Toggle a Demonstration Device?

A visible student/faculty switch is genuinely useful for showing the product. It is also the mechanism by which any visitor grants themselves faculty access. Decide: remove it in favour of an ANCRID-asserted role; retain it only behind an explicit demonstration-environment flag; or keep it and accept that ANCRA has no access control. The third option should be chosen deliberately, not by default.

The Core Learning Flow

Journey → Experience → Lesson

This is the path a student takes to consume content, and the reason ANCRA exists. It is three routes deep.

Inside the lesson player

Observed — The Central Learning Interaction Does Not Function

The lesson player mounts no audio or video element. Pressing play sets a flag that applies a small CSS transform to a still poster image. There is no media source, no timeline, no progress event and no completion signal.

This has a consequence beyond the player itself: because no lesson can be completed, every downstream progress indicator — journey completion, graduation readiness, the portfolio score — is necessarily derived from seeded values rather than student activity. Specifying media playback is the prerequisite for those surfaces meaning anything.

Student Record Surfaces

Decision Required — These Surfaces Are Entirely Passive

None of the seven permits any action. A student can see an assignment but not submit it, see a calendar but not respond to an event, see a team but not join one. Confirm the intent: if these records are produced by faculty action or by other ecosystem modules, each empty state should say which, so the student knows where the record comes from. If a student is meant to act here, those actions need specifying — they do not currently exist.

Applies to All Seven — No Failure State

None of these surfaces distinguishes an empty record from a failed request. A student whose assignment list fails to load sees the same screen as a student with no assignments. For an academic product this is a meaningful misrepresentation and should be corrected across the pattern in one change.

Decision Required — No Student Submission Path Exists Anywhere

Taken together, a student using ANCRA today can browse everything and submit nothing. Assignments cannot be handed in, portfolios cannot be signed, peer reviews cannot be written, projects cannot be started, and the graduation packet cannot be sent.

This is a coherent gap rather than seven separate defects: the application has no student-submission capability at all. It should be scoped and specified as one workstream, with a decision on where submissions are stored and who is notified when one arrives.

Observed — Faculty Cannot Author, Grade or Approve

Across the suite: 18 dead controls and 11 unreadable fields. The consequences are specific. A lesson cannot be published. A rubric cannot be created. An assignment cannot be issued to a cohort. A grade cannot be returned to a student — the Sign & Return control is dead and the feedback textarea cannot be read. On the Approvals surface, Approve is likewise dead.

A faculty member can compose feedback, press Sign & Return, receive no error, and reasonably believe the student has been graded. Nothing was sent and nothing was stored.

AI Course Builder Observed

Decision Required — Simulated Generation

The AI Course Builder shows a loading state for a fixed 1.4 seconds and then reveals fixed content. ANCRA has a working AI integration used by the AIAH dock, so the capability exists. Decide: connect this tool to the configured AI service, or remove the simulated generation. It should not ship presenting fixed text as a generated draft.

Decision Required — The Approval Chain Is Entirely Non-Functional

Approvals is the surface through which faculty accept student work. Both of its controls are dead. Combined with dead grading (page 08) and the absence of any student submission path (page 07), the full submit → review → approve → grade cycle does not exist in any part.

That cycle is the core academic workflow of a learning platform. It should be treated as a single specification and build effort rather than as fifteen individual dead buttons.

Decision Required — Analytics Are Not Derived From Activity

Cohort analytics render from a fixed payload. Because no lesson can be completed (page 05) and no work can be submitted (page 07), there is currently no activity from which real analytics could be computed. Analytics should be specified after the submission and completion paths exist, or the surface should state plainly that figures are illustrative.

Decision Required — What Should a Module Card Do?

These surfaces are ANCRA's expression of the connected ecosystem, and they are the natural place for the cross-module navigation the ANCR architecture describes. Three options: open the real module carrying the user's session; deep-link to a specific view within it; or present the module as informational only and remove the action controls. The current state — actions that look live and do nothing — is the one option that should not ship.

Intended — “Coming Soon” Should Not Offer Actions

A module that has not launched should not present a clickable Notify me at launch control unless that notification is actually registered somewhere. Either wire it to a real waitlist or render the state without actions.

Grouping for Delivery

The faculty half of this register resolves into three coherent workstreams rather than thirty-odd fixes: an authoring pipeline (Lesson Builder, Rubrics, Assignment Builder, Experience Builder, Curriculum Builder — all needing state binding and a destination endpoint); an assessment cycle (Approvals, Grading, Command Centre); and ecosystem integration (all module surfaces, which cannot be wired until the corresponding modules expose entry points).

Suggested Sequence

Several of these are prerequisites for others and should not be scheduled in parallel. Identity first, since nothing else can be safely deployed without it. Then media playback and file upload together, as both are infrastructure that several surfaces depend on. Then the submission and assessment cycle as one workstream, since a submission with nowhere to go is not useful. Progress and analytics last — they can only be truthful once real activity exists to compute from.

Blocking Dependency — No Upload Capability

ANCRA has no file upload anywhere: not for lesson media, not for stems, not for portfolio artefacts, not for assignment attachments. Several flows in this document are specified against an approved media storage service that does not yet exist. This is a prerequisite for the learning and authoring surfaces to function at all, and should be resolved before either is scheduled.
